# Iterwave 业务与技术设计基线

> 状态：T9-D 整理版，作为本仓库后续业务设计与实现验收的唯一规范入口。  
> 来源：总控 Issue #7、早期目标业务架构 PR #1、已审查的 T3/T4/T7/T8 实施约束。  
> 本文定义目标，不代表所有模块已完成或所有早期 PR 已合并。

## 1. 唯一业务闭环

`经营资料 → 原始素材盘点 → AI 经营分析 → 用户确认分析报告 → AI 制定母计划 → 母计划审核生效 → AI 生成平台子计划草稿 → 子计划审核 → 策略步骤 → 生产线 → 生产任务 → 图文成品 → 内容审核 → 用户确认发布 → 发布核验 → 效果反馈 → 经营复盘与策略调整`

任何页面入口、后台任务或兼容 API 都不得绕过这条闭环中的确认、审核、版本和归属门禁。

## 2. 业务对象与层级

1. **账号组北极星**：账号组级长期定位、经营方向、目标用户、核心价值、业务模式、平台关系和长期目标；独立版本化，不与短期进度目标混用。
2. **经营资料与原始素材**：产品/服务资料、素材、知识来源、许可/隐私状态和资源缺口。资料登记不等于素材授权确认。
3. **经营诊断报告**：基于已登记资料与原始素材生成；区分确认事实、推断、外部证据、未知项和待确认项；用户确认后才能作为母计划生成依据。来源资料/素材指纹变化时报告失效。
4. **母计划**：账号组级战略计划，定义经营目标、平台组合、内容方向、产能与节奏；只允许通过计划管理创建/修订，必须草稿—审核—生效。
5. **平台子计划**：母计划在平台维度的执行策略；必须绑定母计划版本，修订不可覆盖历史版本，审核后生效。
6. **策略步骤/阶段**：子计划版本内的执行阶段、目标、依赖、准入条件、完成标准和效果评估；战略定义通过新版本修订，执行结果单独追加。
7. **生产线/生产任务**：生产线策略模板与单条内容执行实例分离；每条内容一个执行实例，每次只决策和生产一条内容，下一条必须在上一条完成审核/发布核验和关闭后重新决策。
8. **内容成品/草稿**：生成、修改、审核、退回、存稿和发布确认是不同状态，不得把 AI 生成或平台草稿保存视为发布成功。
9. **发布核验与效果事实**：只接受用户确认的真实发布证据；指标事实保留来源、时间、时区、状态和真实零值；失败/缺失不得伪造为 0。
10. **复盘与策略调整**：效果反馈和复盘建议关联真实发布内容、指标和计划版本；采纳建议只能创建新草稿，不能直接修改生效战略。

## 3. 战略定义、授权和版本规则

- 计划管理是战略定义的唯一入口；内容日历是排期、历史批次和执行结果投影，不得独立创建战略计划。
- 母计划、子计划、策略步骤和生产线定义必须经过审核才生效。
- API、Store、Worker 均必须执行服务端状态、版本、父子归属、租户和幂等校验；前端隐藏按钮不构成权限控制。
- 子计划版本只能基于当前生效版本创建；旧草稿不得覆盖更新版本；普通修订不得把子计划重绑到另一母计划。
- 生产线版本必须绑定当前有效子计划版本；审核时再次校验基准和父级授权。
- 生产任务必须保存创建时的母计划、子计划、阶段/策略步骤、生产线版本和输入上下文快照；后续计划修改不得改写历史任务。
- 删除采用软删除和受控恢复；历史版本、审计和生产证据不得被覆盖或物理清理来绕过规则。

## 4. 经营上下文与生产门禁

每个生产任务创建前必须从租户数据库组装可追溯的经营上下文，至少包含：
- 当前有效北极星、母计划、子计划、策略步骤/子目标和生产线版本；
- 已确认经营诊断与来源指纹；
- 业务资料、原始素材及其版本、许可/隐私状态；
- 最近已发布内容、有效指标和复盘事实；
- 平台账号身份、资源能力、执行参数及任务输入。

缺少必需事实、来源失效、版本不匹配或读取/解析失败时必须失败关闭。任何人工豁免必须显式记录原因、操作人、范围和证据，不得把系统错误或数据缺失解释为可豁免。

## 5. 单内容生产生命周期

`pending → producing → review_pending → awaiting_save → awaiting_publish → published/verification_pending → verified → feedback_pending → closed`

失败、退回、取消和恢复必须保留原任务身份、尝试历史和快照。新一条内容不能与尚未关闭的单内容生产线并行。

## 6. 发布、复盘与数据回流

- 仅用户明确确认真实发布后，才创建发布核验凭证；保留平台内容 ID、URL、真实发布时间、发布时内容快照与哈希。
- 发布证据不可覆盖；同一草稿的核验写入必须幂等。
- 发布核验通过后通过持久化 Outbox 事件通知生产线关闭；消费者必须具备 claim/lease/ack/retry 和幂等语义。
- 发布后建立独立复盘任务；采集失败不得伪造指标或改变发布状态。
- 统一指标事实应区分有效事实、最新事实、来源、采集时间、时区和采集状态。
- 复盘建议、效果反馈和目标影响必须保留证据及历史；采纳只产生新版本草稿。

## 7. 图文与图片治理边界

- 本项目范围为图文内容，不新增视频生产能力。
- 图片整套或单张重新生成都必须填写理由；新版本默认待审核，原图片保持不变，只有人工采用后才切换当前版本。
- 单张重做必须继承当前已采用整套的视觉基准及相邻页参考；非目标页文件哈希必须保持不变。
- 提示词、结构化指令、视觉基准、参考图、源/输出版本、任务关联和失败原因必须可追溯。

## 8. 数据库与迁移规则

- 迁移必须增量、可重复验证并提供回滚/恢复说明；不得删除或重写历史生产数据、审核证据、任务快照和审计记录。
- 每个租户使用独立数据库、配置和资源目录；API 写请求必须有明确租户上下文，Worker 按任务固化的 tenant_id 构建运行时。
- 版本外键、租户边界、唯一约束、不可变证据和 Outbox 必须由数据库/Store 共同保证，不依赖前端状态。
- 当前早期 PR 的迁移顺序按审查报告执行；迁移号不得因并行开发而重复或乱序。

## 9. 验收原则

- 每个设计条款都要有代码位置、迁移依据、自动化测试和可复制命令。
- 必须覆盖成功、失败、重试、并发、过期版本、跨租户、绕过审核、历史快照和异常恢复。
- CI 通过只证明对应自动化检查通过，不等同于真实平台发布、业务效果或端到端闭环验收。
- 任何未实现能力必须明确标注为未实现/部分实现，不能以设计文档或接口占位冒充完成。
- 子任务独立分支和 PR；CI 与审查通过后再合并。

3. `docs/architecture/PLAN_VERSION_DATA_CONTRACT.md`、`docs/unified-plan-management.md` 等属于具体领域数据/实现契约，只能细化本基线，不能另行定义冲突的业务闭环。
